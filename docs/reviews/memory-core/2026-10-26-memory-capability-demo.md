# 记忆继承：展示方式与本轮实现

## 要证明什么

不是“平台有一个聊天框”，而是：接班人没有参与前一次对话，仍能从已确认记忆中了解进度、失败条件和下一步，并在本地核对代码后继续。

## 本轮网页修改

- 已失败方法从折叠详情移到已完成、阻塞、下一步旁边。
- 明确标注正在查看的记忆，与插件接续实际使用的版本分开；可返回查看接续使用的版本。
- 显示来源会话和父记忆 ID，可查看当前列表内的父记忆修订。
- 不假定父记忆的精确修订号：现有 parentMemoryId 没有这个信息。即使列表只找到一个修订，也不声称它就是继承时使用的修订。
- 不在列表中的父记忆明确显示不可查看；不会借用其他任务的记录。

沿用工程工具界面的条目布局、现有字体和色彩 token，不添加卡片、口号和装饰性状态。遵循 anti-ai-slop-ui 的信息优先原则。

## 建议实际演示：同一个任务，两次工作

1. A 在 VS Code 尝试一个方案，保留真实失败原因与测试输出；整理、确认并同步断点。
2. 网页打开任务，展示已完成、已失败方法、下一步。解释这些来自 A 的工作，不是 B 手填的交接单。
3. B 使用有权限的账号及匹配代码工作区，选择断点，点击“在 VS Code 继续工作”。在插件核对、确认启动。
4. 网页展示收到插件、核对、确认、运行回执。让 B 的 Agent 首先说明继承的失败条件和下一步；对照原记录检查它是否理解正确。
5. B 完成一段工作后，再确认并同步新的记忆。网页展示新进展及父记忆入口。

衡量：交接前后需要人工补充几次上下文、是否重复失败方案、第一项行动是否符合记录。不要用“节省百分之多少时间”等没有测量的数据。

## 边界与下一步

- 自动回执模拟不等于双机真实 Agent 已验证。正式演示要用真实两次会话及代码结果。
- 原始对话没有随此网页材料上传；当前展示的是结构化记忆，不是全部对话。
- 保存断点不是备份整个工作区，未提交代码需另行处理。
- 下一项应补精确父版本引用（revision + digest），再做继承前后差异。不能从时间或“最新修订”猜测继承关系。
- 跨机使用同一个可访问的服务地址；不能把 A 的 localhost 当成 B 可访问的平台地址。

## 本轮验证

新增 3 项父记忆定位测试：多修订不猜版本、任务隔离、无来源/未找到/自引用。没有改任务状态、worktree 操作或插件执行协议。
