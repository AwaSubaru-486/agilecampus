# 网页与插件接续回执

## 范围与操作

本轮对应下一步计划第 1 项：网页与插件双向反馈。进入任务顶部“当前工作记忆”，选择已保存版本后点击“在 VS Code 继续工作”。网页先创建绑定当前账号、任务和固定记忆版本的接续请求，再打开插件。插件核对同一服务/项目/账号，独占接收请求；随后核对本机代码并进入既有启动确认。

网页在同一位置显示：等待插件 → 已收到 → 核对中 → 等待确认 → 启动中 → 已开始工作 → 会话结束。取消、失败和结果待核对分别显示。只有本机启动器收到真实 session 回执、绑定新会话并记录继承材料后，才报告 running；进程创建和 URI 点击均不算 running。会话结束不代表任务验收或当前测试通过。

接续记录默认收起，展开可看状态历史。刷新页面读取服务器上当前用户在此任务的最近一条请求，并显示实际使用版本。未被接收时可重新打开同一请求；10 分钟未被接收的请求不能启动，用户可以重新发起。已被接收的请求不允许重放启动。网页自动刷新两分钟后暂停，并保留手动刷新，不能因没收到新消息就宣称 Agent 已停止。

## 实现契约

- 新表 `task_memory_continuations`。迁移文件 `scripts/migrations/2026-10-26-task-memory-continuations.sql`，依赖前一份 task-memory-versions 迁移，已在本机开发库和独立测试库应用，未清空数据。
- 接口 `/api/projects/{projectId}/tasks/{taskId}/memory/continuations`：GET 读自己的请求；POST 幂等创建；PATCH 仅接受经过 PAT 鉴权的插件 claim/report。浏览器 Cookie 无权提交插件回执；无效 Bearer 不回退到网页登录。
- URI 增加 `request` UUID。URL 不包含 PAT、claimId、命令、文件路径或原始对话。旧无 request URI 保留原行为但没有网页回执；网页新入口总会创建有 request 的链接。
- claim 使用数据库条件更新，同一请求只有一个持有者。丢失 claim 响应时同一插件使用同一个 claimId 重试，其他窗口不能领取。
- report 使用持有者标识和递增序号，重试同一事件不重复追加。服务器检查状态顺序、执行 ID 不可替换、running 必须有会话确认标识。插件只发送状态和执行 ID，不发送原始会话 ID、本机路径、日志正文或执行结果摘要。
- 插件在内存中串行发送回执，网络失败按同一序号重试一次；之后若有新事件，会先重发上一个未确认事件。启动前回执失败阻止启动；启动后回传失败在本机输出通道记录，不把网页故障变成 Agent 的执行失败。
- 启动器通过 `ContinuationObserver` 回调向 URI 桥接报告实际阶段。任务状态机和 worktree 不被此记录修改。

## 界面约束

沿用 `2026-10-26-web-memory-design.md` 的 Developer Tool 方向、已有字体和 panel/ink/stroke 语义色。进度采用任务记忆下的一行状态、固定版本和时间；历史按需展开，不新增仪表盘、统计卡片、渐变或装饰性竖线。anti-ai-slop-ui 约束用于维持动作优先的布局，主观复核模板化程度 2/10、任务针对性 8/10；非客观用户研究分数。
