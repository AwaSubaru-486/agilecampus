# UI 与前端体验学习笔记：简洁、完整、顺手

研究日期：2026-10-08。适用项目：AgileCampus。

## 1. 本次学习要回答的问题

一个功能入口出现在这里，应当是因为用户正在这里需要它。设计的任务是帮助用户找到事情、判断状态、完成操作、继续下一步。

“功能完全呈现”应理解为：功能都有合理归属、入口可以发现、操作结果可以确认。无需把全部按钮同时放在每个页面。

本次阅读了 Linear、Notion、Atlassian 的官方产品说明，IBM Carbon 与 GOV.UK 的组件示例及交互指南，以及 NN/g 和 W3C 的设计依据。未登录体验这些产品的完整付费工作区；下文明确区分官方做法与针对本项目的设计建议。建议尚未经过 AgileCampus 真实用户测试，不代表已经实现或证明有效。

## 2. 从别人那里学到什么

### Linear：让项目、任务和视图有清楚的关系

官方做法：项目概览承载说明、资源和里程碑；项目属性可以通过详情侧栏访问。筛选后的任务和项目集合可保存为视图，并收藏以便再次访问。[项目概览](https://linear.app/docs/project-overview)、[自定义视图](https://linear.app/docs/custom-views)。

本项目可借鉴：在任务列表保留“我的任务、待验收、本轮任务”这样的工作视图。选中任务后显示详情，关闭详情仍回到同一个筛选结果。资源属于项目背景，提交属于任务动作，不能因为都与项目有关就混放在工具条。

适用边界：学生和导师不一定熟悉专业项目管理术语。“视图”先呈现为有意义的中文分类；自定义规则可作为进阶能力。

### Notion：稳定归属，加上个人捷径

官方做法：侧栏支持收藏、团队空间和嵌套页面；可固定数据库视图，也可以折叠侧栏分组。[侧栏导航](https://www.notion.com/help/navigate-with-the-sidebar)。

本项目可借鉴：全局入口保持稳定，最近使用或收藏的项目成为额外捷径。用户知道完整功能放在哪里，也能快速返回自己常做的事情。

适用边界：自由嵌套会增加维护和寻找成本。AgileCampus 的业务结构相对明确，应先提供默认归属，避免让新用户自己搭建整套导航。

### Atlassian：区分全局动作与业务导航

官方设计说明强调导航可预测、允许用户定制，并逐步展开复杂内容；将产品导航放在侧栏，顶栏承担搜索与创建等通用动作。[新导航设计过程](https://www.atlassian.com/blog/how-we-build/designing-atlassians-new-navigation)。

本项目可借鉴：侧栏回答“去哪里”，项目导航回答“这个项目现在做什么”，内容区回答“对当前对象执行什么”。全局创建如果没有明确对象，应先选择创建类型和目标团队或项目。

适用边界：无需机械复制大型企业产品的所有导航层级。若两层导航使用相同分类和名称，就应该合并或重新划分职责。

### IBM Carbon：操作随对象和选择状态出现

官方示例区分表格工具条、行操作与批量操作。选中条目后出现批量操作栏；补充信息可展开，内容复杂时使用详情页或侧面板。触屏上的更多操作入口不能只靠悬停出现。[数据表设计指南与示例](https://www.carbondesignsystem.com/building-blocks/core/components/data-table/guidelines)。

本项目可借鉴：筛选属于整个列表；修改负责人属于某项任务；批量分配只在选择多项任务后出现。把次要操作收进“更多”，同时保留常用操作的文字入口。

适用边界：不要将主流程的“提交成果”和“验收”藏进更多菜单。桌面高密度表格也不应原样缩进手机屏幕。

### GOV.UK：用任务、状态与可恢复错误建立信心

官方任务模式面向跨多次访问完成的较长流程，说明任务及完成状态；建议先简化流程，再决定是否需要任务列表。尚不能开始的任务应呈现明确状态。[完成多个任务](https://design-system.service.gov.uk/patterns/complete-multiple-tasks/)。

官方错误模式要求保留已填内容，在字段附近给出错误，并提供顶部错误摘要和焦点定位。[从输入错误中恢复](https://design-system.service.gov.uk/patterns/validation/)。

本项目可借鉴：进入项目先知道本轮还差哪些动作。无法集成时显示“还有两项任务待验收、一项交付未登记”，并链接到可处理的位置。提交失败时保留成果说明，避免让用户重新填写。

适用边界：协作不是人人严格依次完成的一张个人申请表。并行任务和等待他人必须分别表达；不能为了界面整齐而人为增加步骤。

### NN/g：减少记忆负担，谨慎展开复杂性

渐进披露先显示重要内容，将次要或复杂选项放在可识别的后续入口；入口和层级必须易于理解。[渐进披露](https://www.nngroup.com/articles/progressive-disclosure/)。

识别通常比凭记忆回想容易。文章也指出，与当前页面有关的上下文提示，比要求用户记住整套教程更有帮助。[识别与回忆](https://www.nngroup.com/articles/recognition-and-recall/)。

本项目可借鉴：入口文字写“登记交付分支”，而非只有图标。教程围绕原页面当前动作，用户操作后收到反馈。功能仍需有稳定入口，不能以“新手教程里讲过”为理由删除提示。

## 3. 我提炼出的设计判断方法

以下是针对 AgileCampus 的推导，不是某个产品的原文规则。

每新增或移动一个功能入口，先填写这六个问题：

| 问题 | 必须得到的答案 | 例子：提交成果 |
| --- | --- | --- |
| 谁需要它？ | 角色和对象关系 | 有执行权限的任务负责人 |
| 为什么此刻需要？ | 当前任务与状态 | 已认领，准备交付 |
| 操作作用于什么？ | 明确对象和范围 | 当前选中的任务 |
| 最合适的地方？ | 用户已掌握必要信息的位置 | 任务详情中完成标准与交付要求之后 |
| 什么时候不展示或不能操作？ | 权限、依赖、状态原因 | 未认领、已提交、无权限等情况分别解释 |
| 成功或失败后怎么办？ | 结果、下一步、恢复路径 | 显示待验收；失败保留输入并允许重试 |

主操作默认保留一个视觉中心；只有用户确实需要比较的选项才并列强调。例如导师可以同时看到“通过”和“退回”，但任务成员无需面对所有管理、验收和执行按钮。

“更少按钮”“更少点击”“更大留白”都不是独立目标。需要比较寻找成本、误操作、阅读时间、切换后丢失的上下文，以及完成任务所需的总努力。

## 4. AgileCampus 已有基础与待验证问题

本次只读了相关代码，没有进行新一轮界面或权限实测。

- `src/app/(app)/today/page.tsx` 已使用待回应队列，而非单纯展示模块入口。应保留这条方向，验证排序是否真正匹配用户优先级。
- `src/app/(app)/projects/[projectId]/_shared/project-navigation.tsx` 已区分任务执行、规划与迭代、AI 协作、成果与复盘。需要验证子导航是否让用户产生重复选择和“我到底在哪”的疑问。
- `src/app/(app)/projects/[projectId]/_console/console-shell.tsx` 已采用任务列表与详情，执行记录按需展开。无需推倒重做，应重点验证返回列表时筛选、滚动和选中任务是否保留。
- `src/app/(app)/projects/[projectId]/_console/task-contract-panel.tsx` 已按状态和权限提供操作，并展示验收权限说明。待验证的是长详情里关键动作是否被背景材料淹没。
- `src/lib/tutorials/catalog.ts` 已列出多类功能课程。目录可辅助覆盖检查，但不等于每项能力都已经完善，也不能代替日常入口的可发现性。

历史审查 `docs/design/anti-ai-slop-review.md` 已提出减少等权卡片、突出协作现场。新的学习结论补充操作和导航依据，不重新制造一套与它冲突的视觉风格。

## 5. 建议的功能归属：完整可找，不在首屏堆满

下面是布局建议，并非当前页面功能实测结果。网页与外部工具的能力边界应保持清楚。

| 用户要做的事 | 主要归属 | 当场出现的入口 | 次要或进阶入口 |
| --- | --- | --- | --- |
| 知道今天要处理什么 | 今日 | 我的执行、待回应、待验收队列 | 查看全部、筛选 |
| 进入某个项目 | 项目列表及最近项目 | 项目名、当前阶段、最近状态 | 收藏、归档等管理动作 |
| 创建或加入团队 | 我的团队 | 创建、邀请码加入 | 已有团队管理 |
| 管理成员与角色 | 团队成员页 | 成员名单、角色、邀请 | 权限允许的角色调整 |
| 创建项目 | 目标团队的项目页 | 在此团队创建项目 | 日期等可选属性 |
| 生成一轮任务 | 项目规划页 | 需求输入、生成草案 | 模型配置链接及失败恢复 |
| 调整与发布草案 | 草案编辑区域 | 负责人、完成标准、保存、发布 | 批量修改、详细参数 |
| 执行任务 | 执行台任务详情 | 要求、认领、计划、提交 | 契约历史、技术细节 |
| 查看看板、标签 | 任务列表的视图与筛选 | 列表/看板切换、标签筛选 | 团队标签维护 |
| 审核成果 | 待验收队列及任务详情 | 标准、证据、通过/退回、意见 | 历史审核记录 |
| 推进阶段集成 | 当前阶段底部 | 缺项、交付登记、提交集成 | 集成记录、分支详情 |
| 开始下一轮 | 规划与迭代 | 当前阶段之后的新增需求入口 | 过去阶段和完整时间线 |
| 请求帮助 | 当前任务附近 | 携带任务背景的求助入口 | 协作中心汇总 |
| 使用 AI | 当前任务或项目的 AI 区域 | 任务背景、输入、建议、待确认 | AI 成员配置、运行记录 |
| 使用共享资源 | 团队资源页 | 资源可用情况、登记、结束占用 | 使用历史与统计 |
| 查看成果与贡献 | 项目成果与复盘 | 交付材料、过程记录、贡献说明 | 活动流、跨项目资料库 |
| 连接 VS Code 或外部工具 | 账号与连接 | 配置指引、连接状态 | 令牌、采集和诊断细节 |
| 配置通知 | 账号与连接 | 通知和绑定设置 | 低频账户配置 |
| 学习某个功能 | 侧栏教程目录、功能旁帮助 | 当前功能教程、原页面续练 | 完整示例项目主线 |

两个入口可以指向同一个操作：待验收队列让导师快速找到任务，任务详情让导师看完证据后审核。这是合理的场景入口；应复用同一操作和结果，避免产生两套不同流程。

## 6. 三种角色的首页与任务动作

### 按责任安排注意力

| 角色 | 首页先看什么 | 打开任务后最需要什么 | 低频功能放在哪里 |
| --- | --- | --- | --- |
| 组员 | 我的任务、退回修改、阻塞回应 | 目标、完成标准、交接材料、执行与提交 | 完整历史、外部运行诊断 |
| 组长 | 本轮缺项、待分配、成员阻塞、待审核事项 | 分工、执行情况、缺失证据及合法下一步 | 成员配置、标签与 AI 配置 |
| 导师 | 待验收与待集成审核、需介入的阻塞 | 对照标准看证据，再写意见并决定 | 完整活动和长期贡献记录 |

角色属于实际团队与项目上下文。一个人在不同项目可以承担不同责任，不应全站永久锁死一个角色视图。

### 按状态组织动作

| 情况 | 页面应该告诉用户 | 主要操作建议 |
| --- | --- | --- |
| 任务未认领且可认领 | 我需要完成什么、接住意味着什么 | 确认认领 |
| 本人正在执行 | 完成条件、当前计划、交付要求 | 提交成果；附近保留求助 |
| 已提交待验收 | 已提交给谁、当前等待什么 | 查看提交记录，通常不再显示重复提交 |
| 被退回 | 为什么退回、具体修改点 | 修改并再次提交 |
| 有审核权限的待验收任务 | 标准与证据如何对应 | 通过或退回，填写必要意见 |
| 阶段尚不能集成 | 还缺哪些项、由谁完成 | 跳到缺项，而非只显示灰按钮 |
| 无权限或需他人处理 | 原因与责任人或角色 | 查看进度或联系协作者 |

以上由后端真实状态与权限决定。设计只能改善呈现，不能允许拖动看板直接绕过验收，也不能自动替导师确认成果。

## 7. 一个任务详情应如何排布

建议用一条纵向主线：

```text
任务名称 · 所属阶段 · 负责人 · 当前状态
目标 / 完成标准
必要交接资料
当前成果与审核意见（存在时）
当前状态允许的主要动作 + 就近的求助
更多资料：历史 / 分支 / 外部运行 / 检查点
```

用户要一边看标准一边提交或验收。桌面可采用列表与详情并排；手机采用列表 → 详情，返回时保留原任务位置。不要为了缩短页面而把标准和提交表单拆成互不相见的两个页面。

将用户目标与系统实现分开：“提交成果”是主动作；head SHA、会话事件、检查点字段是特定工作流的技术材料。技术材料对需要它的人仍完整可达，在当前任务需要时展开。

## 8. 视觉简洁必须帮助阅读和操作

以下尺寸和布局均为本项目候选值，应做实际验证，不是普遍标准。

- 同类任务优先用对齐的列表行；独立编辑或确认流程才使用卡片。避免卡片里继续套卡片。
- 以标题、间距和细线表达分组，主色用于当前选择与重要操作。错误、成功和等待均有文字，不能只靠颜色。
- 中文正文可从 14–16px、舒适行高开始试验。辅助信息与正文区别明确，关键原因不能缩成难读的小字。
- 使用统一间距档位，例如 4/8/12/16/24/32；这些数值只是候选设计 token，应随页面密度调整。
- 边界和状态保持稳定。列表行、任务详情、抽屉和弹窗分别服务不同关系，不统一套大圆角和阴影。
- 图标辅助识别，核心业务操作有文字。触屏不能依赖悬停；快捷键是熟练用户捷径，不能成为唯一入口。

W3C WCAG 2.2 的目标尺寸最低要求是 24×24 CSS 像素，带有间距等例外；它不是“所有按钮必须 44px”的规定。AgileCampus 可将手机常用点击区域至少约 44px 作为更宽松的产品目标。[目标尺寸最低要求](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)。

有键盘焦点的组件不能被作者创建的内容完全遮住。教程卡片、固定按钮栏和弹层都应检查这种情况；本项目进一步要求关键输入和提交按钮尽量完整可见。[焦点不被遮挡最低要求](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html)。

## 9. 前端实现要支持这些体验

以下是应用层实现建议，不指定或引入新的组件库。

1. **先写功能位置清单。** 每项功能记录角色、对象、状态、主入口、补充入口、保存结果和失败恢复。组件拆分跟随这个清单，避免后端新增一个接口，前端就随手新增一个按钮。
2. **保持一套动作语义。** 队列与详情共用任务动作；前端显示条件不得成为权限依据，服务端仍校验。业务状态与教程状态分开，教程读取真实操作结果。
3. **保存浏览上下文。** 项目、任务、筛选、视图和选中对象有明确恢复规则；返回列表保留滚动位置。URL 可保存可分享的视图参数，敏感输入不写进 URL。
4. **区分提交中、成功、失败和等待他人。** 请求发出后防止重复提交；成功更新实际状态；失败保留字段和明确重试。只展示“已保存”而列表不更新，也会破坏信任。
5. **按需加载进阶内容。** 外部运行、长历史等打开时再获取；已经填的内容不能因切换折叠区域或重渲染而丢失。
6. **统一基础组件。** 按钮、字段、状态、错误、空态、列表与动作区域各有稳定样式和语义。先统一日常工作页面的操作语言，再讨论装饰。
7. **教程定位到具体动作。** 高亮实际输入或操作区域，避免框住整块超长详情。找不到入口时区分数据缺失、权限、加载失败和选错项目；不能统一要求用户“先完成准备”。

## 10. 按价值推进改造，而非再做一次全站换皮

| 顺序 | 工作内容 | 完成依据 |
| --- | --- | --- |
| P0 | 列功能归属，走通组员认领/提交、导师验收、组长规划三条链路 | 无重复流程；每项能力有明确可发现入口 |
| P0 | 调整任务详情动作、缺项原因与错误恢复 | 用户看完标准能直接完成当前操作 |
| P1 | 保留列表上下文，整理列表/看板/时间线职责 | 返回、刷新和切换项目不意外丢失位置 |
| P1 | 教程围绕真实目标分段，明确暂停、完成与恢复 | 每段产生可确认结果，浮层不挡操作 |
| P2 | 统一排版、间距、图标、列表与面板 | 同类交互一致，关键内容阅读更快 |
| P2 | 收藏、常用视图、搜索与快捷键 | 高频用户减少重复寻找，首次用户仍能发现入口 |

教程可以保留完整主线，但建议允许按“创建与规划、执行交付、审核与迭代”分段续练。不能为了让用户熟悉所有功能，强迫每次登录都走长教程。

## 11. 怎样证明用户用着顺手

建议先找 5 位接近目标用户的人做一次形成性测试，覆盖三角色。小样本用于发现问题，不用于宣布统计显著的提升。每人先尝试不看教程完成核心任务，再观察帮助是否有效。

| 测试任务 | 观察内容 |
| --- | --- |
| 第一次登录，找到自己的下一项工作 | 首次点击、是否误入配置或总览 |
| 新建项目，生成并发布一轮任务 | 是否理解草案与正式任务区别 |
| 认领、提交，然后回列表继续 | 是否找到入口、是否丢失输入和筛选 |
| 导师查看证据并退回 | 是否理解责任、修改原因是否留给执行者 |
| 组长发现集成缺项 | 是否能找到缺项并说明谁需要处理 |
| 手机学习中暂停，刷新后续练 | 是否恢复同一项目、任务与操作结果 |

记录完成率、完成时间、误入页面、求助次数、丢失输入、误解状态和用户原话。先收集当前版本基线，再比较同一任务的改造版本。

建议验收条件：核心任务首次操作无需别人指路；每项功能有可发现归属；关键步骤不要求用户记住隐藏图标；错误保留输入且可恢复；手机可完成提交与验收；权限原因和阶段缺项具体可读。时间与点击数目标在基线测量后制定，不凭空宣称“提升多少效率”。
