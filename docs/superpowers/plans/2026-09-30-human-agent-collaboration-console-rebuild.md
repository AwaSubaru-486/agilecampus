## 1. 产品主线：不是聊天，是共同执行

AgileCampus 的核心不是“AI 能回答问题”，而是“一个人把任务交给 Agent，Agent 依据冻结的上下文执行，执行过程中留下可检查的中间结果，另一个人或另一个 Agent 可以从明确断点继续，最后由人验收”。

所有页面都必须服务于以下闭环：

```text
人定义目标
  → 人填写交接契约
  → 冻结 Context Pack
  → 分配给人或 Agent
  → Agent Run 执行并写入事件/证据
  → 遇到阻塞时提出明确输入请求
  → 人补充信息、继续执行或从断点分支
  → Agent 提交可验收结果
  → 人审核、退回或通过
  → 结果进入项目记录
```

### 1.1 五秒可理解原则

用户进入项目后的五秒内必须能回答：

- 当前项目最需要处理的任务是什么；
- 这个任务现在由谁负责，是人还是 Agent；
- Agent 是否正在运行、卡住、失败或等待人确认；
- 上一次执行停在哪里；
- 我现在能做的唯一主要动作是什么。

如果一个页面只能看见聊天记录、漂亮的卡片或统计数字，却看不见上述五项，就视为没有体现主线。

### 1.2 一等对象

页面和交互必须把以下对象当作一等对象，而不是把它们藏在“更多”或聊天气泡中：

- `Task`：人要交付的工作单元；
- `AgentRun`：一次可追踪、可继续、可失败的 Agent 执行；
- `Handoff`：把目标、完成标准、证据要求和截止时间交给执行者的契约；
- `ContextPack`：本次执行实际看到的冻结上下文；
- `Evidence`：证明执行结果的文件、链接、测试、运行记录或文本；
- `Decision`：需要人确认的取舍及其来源。

“AI 协作”不是一个单独的聊天页面，而是这些对象之间的可视化关系。

## 2. 当前问题与重构结论

当前项目页按 `live / work / studio / record` 拆成四个空间，导致用户要在多个入口之间猜测“任务在哪里”“AI 在哪里”“执行是否还在继续”。`ChatPanel` 以对话为中心，Agent Run、上下文冻结、事件和证据被压到聊天下方；`TaskDrawer` 只能看任务详情和审核动作，不能形成一条完整的执行链；`live` 的接力摘要是展示，不是可操作的证据链。

因此本轮不是再增加一个 AI 页面，而是把 `work` 重做成统一执行台：任务列表、任务契约、Agent 执行轨和人工确认在一个连续工作面内完成。`studio`、`live` 作为兼容入口保留，但不能再拥有另一套独立的核心流程。

## 3. 目标信息架构：严格两级导航

全站只保留两级导航：

- 一级：`今日`、`项目`、`协作中心`；
- 二级：当前一级下的实际工作入口。

项目下的二级入口固定为：

1. `执行`：统一执行台，默认进入；
2. `Agent`：Agent 收件箱、运行记录、待人工确认；
3. `记录`：证据、决策、活动审计和成果归档。

不要再新增第三级导航。任务、会话、审批、上下文包必须通过当前二级页面里的选择、抽屉、分栏或 URL 深链打开，而不是再制造一层标签栏。

### 3.1 路由兼容要求

现有链接不能失效：

- `space=work`：成为新的默认统一执行台；
- `space=studio`：作为“Agent”二级入口，复用执行台组件，以运行列表和选中运行作为主内容；指定会话只打开其已授权的来源详情；
- `space=live`：旧链接规范化为 `space=work` 并保留现有过滤条件；没有旧过滤条件时不添加新过滤；不得继续维护独立的重复工作面；
- `space=record`：保留为记录页；记录中的证据和决策必须能反链到任务与 Agent Run；
- `task`、`conversation`、`approval`：继续作为 URL 状态，刷新、复制链接、浏览器前进后退都要恢复选择状态。

现有 `page.tsx` 的重定向逻辑必须先画出兼容矩阵再改，禁止直接删路由。任何旧入口都必须能到达同一个任务执行状态。

## 4. 目标页面：统一执行台

在 `space=work` 下实现一个三面板执行台。三面板是同一个工作流的不同观察角度，不是三个独立页面。

```text
┌ 项目名称 / 搜索 / 过滤 / 新建任务 ──────────────────────────────┐
├ 任务列表（左） ─────┬ 任务契约与交付物（中） ─┬ Agent 执行轨（右） ┤
│ 待处理、进行中、待验收 │ 目标、完成标准、上下文包 │ 当前 Run、事件、输入请求 │
│ 任务行而非装饰卡片     │ 责任人、证据、审核动作   │ 继续、分支、提交验收     │
└──────────────────────┴────────────────────────┴─────────────────────┘
```

### 4.1 顶部工具行

顶部只放工作所需控件：

- 项目名称和当前项目权限；
- 任务搜索；
- 状态、负责人、是否有阻塞、是否等待人工确认的过滤；
- 列表/看板切换（默认列表）；
- 新建任务一个主按钮。

不要放欢迎语、产品口号、虚构指标、装饰性渐变或“智能工作台”之类的标题。统计数字只能在有明确操作意义时出现，例如“待人工确认 2”，点击后必须能过滤出对应任务。

### 4.2 左侧任务列表

任务列表按人能采取行动的优先级排序：

1. 等待我确认；
2. Agent 已阻塞或失败；
3. 我的进行中任务；
4. 其他进行中任务；
5. 待开始；
6. 已完成（默认折叠）。

每一行只显示：任务标题、责任人类型与名称、任务状态、Agent Run 状态、截止时间和一个当前主动作。不要把同一字段在角标、标题、副标题和底部重复四次。

列表行使用分隔线和紧凑留白，不使用一整墙圆角卡片。选中行通过背景/边框和键盘焦点表达，不能依赖彩色竖线、虚线方框、发光阴影或渐变。

状态必须分开显示：

- 任务状态：待开始、进行中、待验收、已完成；
- Agent Run 状态：排队、已派发、运行中、已完成、失败、已取消；
- 阻塞：单独显示“需要输入”或“阻塞”，不能把阻塞伪装成任务状态。

拖拽只允许在已有的非状态分组中调整排序；禁止跨状态拖拽导致“待完成”直接变成“已验收”。状态变更必须走明确按钮和后端状态规则。

### 4.3 中央任务契约面板

选中任务后，中央面板依次显示：

1. 任务标题、任务状态、当前责任人；
2. `handoffBrief`：要完成什么；
3. `doneCriteria`：什么条件算完成；
4. `requiredEvidence`：必须留下什么证据；
5. `responseDueAt`：响应截止时间；
6. Context Pack：冻结状态、版本、包含的来源；
7. 已提交证据及其来源；
8. 审核记录和最近一次退回原因。

底部只给出符合当前状态的一个主要动作，例如“冻结上下文”“开始 Agent 执行”“请求人工输入”“继续执行”“提交验收”“通过验收”“退回并说明原因”。次要动作放在明确的更多菜单中，不同时摆出五个同等权重的蓝色按钮。

### 4.4 右侧 Agent 执行轨

右侧不是聊天气泡列表，而是可读的执行轨：

- Agent 身份、运行时、能力和最近在线时间；
- 当前 Agent Run 的状态、开始时间、耗时、优先级；
- 最近一次已记录的进展（取自活动、消息或运行结果；普通日志不能称为可恢复 checkpoint）；
- Agent 做过的工具调用/输出摘要；
- 待人工输入或审批；
- 产生的证据；
- 下一步建议及其触发条件。

时间线中的每一项必须标明执行者是人还是 Agent，并可跳转到来源消息、活动事件、审批或证据。不要把“AI 正在努力”“卡住的活不会自己变好”之类拟人化文案放进产品；使用可验证的工程状态，例如“运行中”“等待输入”“失败：错误信息可展开”。

右侧主动作规则：

- `queued/dispatched/running`：显示“查看执行”和“请求停止”（只有后端已支持时才显示停止）；
- 存在真实未解决 blocker：显示“查看阻塞”；已有补充输入操作才显示“补充输入”；会话分支必须标为“从此消息创建会话分支”；
- `failed`：显示“查看错误”；重跑操作仅在真实用户鉴权执行入口已验证时显示；
- `completed`：先看任务的真实状态，`review` 显示“查看证据”；提交因证据不足失败时显示缺项，不再次自动提交；
- 无 Agent Run：显示“暂无执行记录”；不能因为分配了 Agent 就宣称运行已启动。

## 5. 状态与领域边界（不可自行改写）

现有领域模型已经把任务和 Agent Run 分开。下游不得为了 UI 方便新增 `agent` 任务状态，也不得把 Agent 完成直接写成任务完成。

### 5.1 固定状态语义

- Task：`todo / doing / review / done`；
- AgentRun：`queued / dispatched / running / completed / failed / cancelled`；阻塞通过真实 blocker 表达，不能用假状态代替；
- ContextPack：正式交接目标要求使用冻结版本；本轮只展示和复用已有校验，不为此改写当前任务或运行状态机；
- Agent 完成：当前 `reportAgentRun` 会写运行证据并尝试提交；只有 `submitTask` 校验成功才进入待验收，校验失败时保留真实任务状态；
- 人通过验收：才允许进入已完成；
- Agent 失败：任务仍归属于原责任人，保留错误和可重试入口；
- Agent 阻塞：运行记录保留为进行中，创建真实 blocker，等待人处理。

### 5.2 现有代码作为事实来源

实现前必须阅读并复用：

- `src/db/schema.ts` 中 `tasks`、`agentRuns`、`contextPacks`、`evidenceItems`、`blockers`、`decisions`、`activityEvents`；
- `src/lib/handoff.ts` 的交接字段和版本校验；
- `src/lib/agent-run.ts` 的收件箱、排队、运行上报、证据和状态规则；
- `src/lib/activity-feed.ts` 与 `src/lib/activity.ts` 的权限和审计事件；
- 现有 conversations、fork、approvals、context-pack API。

第一阶段不改 `src/db/schema.ts`、`src/lib/task.ts`、`src/lib/task-status.ts`、`src/lib/agent-run.ts` 和现有 API。若确实缺少 checkpoint 或执行续接所需字段，先在 `docs/superpowers/plans/` 单独写后端缺口计划，经确认后再动 schema。

## 7. 关键交互的可执行规则

### 7.1 进入项目

进入 `space=work` 时：

1. 优先读取 URL 中的 `task`；
2. 没有 `task` 时，选择第一个需要当前用户处理的任务；
3. 再没有时选择第一个未完成任务；
4. 项目为空时显示“创建第一个任务”，不要显示虚构指标或大段介绍。

选择任务只更新 `?task=`，不触发整页跳转；刷新后恢复同一任务；浏览器返回恢复上一选择。

### 7.2 交给 Agent（后端能力具备后的目标）

“开始 Agent 执行”前必须检查：

- 任务有交接简述、完成标准和必要证据要求；
- Context Pack 已冻结且版本与任务的 committed 版本一致；
- Agent 有可用运行时和权限；
- 没有同一任务的活动运行（除非后端明确允许并显示并行原因）。

检查失败时显示具体缺项和修复动作，不弹一个泛化错误。执行必须走已有的排队/运行 API 或 server action，不能由客户端把任务状态改成“运行中”。

### 7.3 继续、分支和人工输入

- 只有存在真实运行恢复接口时才显示“继续执行”；当前继续聊天不能标为恢复代码执行；
- “从此消息创建会话分支”调用现有 conversation fork API，并显示父会话、来源消息；不能推断对应的运行记录；
- 人工补充内容要记录为消息、活动或 blocker 解决说明，不能只存在 React state；
- 不做自动交接。只有用户明确点击并确认后，才把任务交给下一位人或 Agent；
- 分支要能看到父会话、分支原因和新执行起点。

### 7.4 验收

Agent 完成后右侧显示“查看证据”；以数据库中的任务状态为准。任务已进入 `review` 时不要重复显示“提交验收”。有审核权限的人可以：

- 通过：记录审核人和时间，任务进入 `done`；
- 退回：必须填写原因，任务回到可执行状态并保留退回次数；
- 查看来源：回到原运行记录或从有权限的消息创建会话分支；不承诺恢复原进程。

## 8. 视觉与前端实现约束

本次采用“开发者工具 / 工程控制台”方向，而不是营销 SaaS 或 AI 聊天产品。

### 8.1 必须遵守

- 中性石墨/灰阶作为基础色，蓝、青、绿、橙只表达可验证状态；
- 系统无衬线字体用于界面，等宽字体只用于 ID、路径、日志、代码和运行输出；
- 用分隔线、列标题、表格/列表行、紧凑留白组织信息；
- 详细信息放在分栏、抽屉和可展开区域，不用卡片墙；
- 动画只服务于面板打开、运行状态变化和加载反馈；支持 `prefers-reduced-motion`；
- 所有交互可用键盘和屏幕阅读器完成，焦点状态必须可见。

### 8.2 明确禁止

- 页面/分区/抽屉标题下的介绍性副文案全部删除，不另写同义解释。保留真实数据、用户内容，以及影响操作的字段要求、错误、权限和图例信息。详见逐单施工手册“标题文案硬规则”。

- 大面积圆角蓝底卡片、紫色 AI 渐变、霓虹发光和玻璃拟态；
- 欢迎语、鸡汤式副标题、“卡住的活不会自己变好”等拟人化文案；
- “一个点 + 一串解释”的 AI 生成式描述；
- 重复的项目状态/任务进度/Agent 入口小卡片；
- 为了显得丰富而虚构指标、趋势图、活跃度或进度百分比；
- 使用彩色竖线、虚线方框、装饰性点链来代替真实层级；
- 默认把所有页面做成卡片列表；
- 新增一个只会聊天的 AI 页面；
- 把人和 Agent 混成一个模糊“团队成员”标签；
- 用前端乐观状态绕过后端权限、审核或任务状态机。

## 10. 端到端验收剧本

以下是长期完整产品的目标剧本，不是本轮全部能力已存在的声明。本轮按逐单施工手册中的 A（必须可验证）/B（需后端能力）分开验收。B 缺失必须报告，不能用模拟按钮、假数据或继续聊天替代真实运行：

1. 创建一个带完成标准和证据要求的任务；
2. 在任务契约面板冻结 Context Pack；
3. 把任务分配给 Agent，启动一次运行；
4. 在 Agent Run 中看到排队、运行中和事件；
5. 模拟 Agent 请求人工输入，页面显示具体阻塞原因；
6. 人补充输入后选择“继续执行”；
7. 再从同一 checkpoint 选择“从此处分支”，确认父会话和分支原因可见；
8. 模拟 Agent 完成，确认生成运行证据，任务为待验收而不是已完成；
9. 人退回一次，确认原因和运行记录保留；
10. 人通过验收，确认任务进入已完成并能在记录页反链到证据、决策和活动；
11. 复制包含 `task/conversation/approval` 的 URL，在无刷新和刷新后都能恢复正确面板；
12. 用无权限账号验证私有会话、Context Pack 和审批不会泄露。

## 11. Definition of Done

以下是完整产品目标。仅完成施工手册验收 A 时应报告“协同工作面重构完成”；必须同时完成验收 B 并满足以下条件，才可以说“人-Agent 执行交接完整落地”：

- 默认项目页是统一执行台，而不是聊天页或指标仪表盘；
- 两级导航中能直接找到执行、Agent、记录；
- 一个任务的契约、执行、阻塞、断点、证据、审核在同一上下文可追踪；
- 人和 Agent 的身份、状态和权限明确分开；
- Agent 完成不会绕过人工验收；
- 继续执行和从断点分支是明确的用户操作，而非自动交接；
- 旧路由可用，URL 深链、刷新、返回行为稳定；
- 没有卡片墙、装饰性 AI 文案、虚构指标和状态混淆；
- 通过 lint、类型检查、构建、UI 文案检查和端到端验收剧本；
- 最终交付说明能用三句话回答：人交付了什么、Agent 做了什么、谁在什么证据基础上做了最后决定。

## 12. 绝对不要做的事

- 不要先做视觉换肤，再补协同逻辑；
- 不要复制一个外部模板的完整页面并保留其营销信息架构；
- 不要新建一个“AI 助手”入口来掩盖执行状态缺失；
- 不要因为 UI 需要而修改 Task/AgentRun 状态机；
- 不要把 Agent 的输出直接当作已验收结果；
- 不要自动把任务交给下一位执行者；
- 不要通过拖拽跨状态改变任务；
- 不要隐藏失败、阻塞、拒绝和审核记录；
- 不要在本计划未授权的范围内重写后端、数据库、认证或扩展端；
- 不要在没有实际验证的情况下声称“已经实现 Agent 断点交接”。
