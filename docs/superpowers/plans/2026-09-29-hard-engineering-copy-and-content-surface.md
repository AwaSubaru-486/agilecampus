# AgileCampus 工程化文案与信息层级重构计划

> 状态：待执行。本文是一次内容与信息层级重构的施工计划，不在本阶段直接修改业务页面。
>
> 目标：把网页端从“解释产品理念的展示页”收敛为“可直接操作的工程控制台”。页面只回答四件事：当前对象是什么、状态是什么、谁负责、下一步能做什么。
>
> 范围：可见文案、标题层级、状态呈现、空状态、元数据布局、项目空间内的信息密度和导航提示。保留现有业务逻辑、权限、路由、任务状态机、AI 会话和 API 契约。

## 1. 问题定义与完成标准

### 1.1 当前问题

仓库中存在三类会让页面像 AI 生成的产品宣传稿、而不像工程工具的内容：

1. **产品口号代替对象名称**：例如“一个项目不该只剩聊天记录”“你带的项目眼下都还稳”“有人在等搭手”。它们表达态度，但没有告诉用户要操作哪个对象。
2. **装饰性副标题和人格化 AI**：例如全大写的 `AI TEAMMATES`、`现场 / 实时状态`、`人、Agent、阻塞和下一步`，以及“像人一样被指派”“自己接活、会举手”等拟人化描述。这些文字增加阅读成本，也模糊了责任边界。
3. **用点号、破折号、斜杠把多个字段串成一句**：例如“反馈 · 文档 · 成果”“1 项推进中 · 2 项需要关注”。它看起来像营销卡片或 AI 摘要，而不是可扫描的工程数据。

### 1.2 目标状态

- 一级标题直接命名页面对象：`今日`、`项目资料`、`项目健康度`、`AI 成员`、`决策记录`。
- 每个工作区的首屏在 5 秒内能读出：对象、状态、负责人/参与者、截止时间、下一动作。
- 统计信息使用对齐的字段、表格或键值行，不再用一整句点号链承载多个事实。
- AI 的能力用“模型生成了什么、谁确认、写入哪里”说明，不使用人格化或拟人化措辞。
- 空状态最多两行说明，并提供一个明确动作；不写产品愿景或情绪化安慰。
- 保留现有 URL、`space`、`task`、`conversation`、筛选条件、Server Action、权限和任务状态流转。
- 受限屏幕宽度（约 615px）和桌面宽度（>= 1024px）都能完成核心路径：今日 → 任务 → 接手/请求协助/继续 AI 协作 → 提交 → 人工验收。

## 2. 参考原则：借成熟模板的组织方式，不复制博客页面

本次只借鉴结构和工程规范，不引入博客的 MDX、Contentlayer、文章路由或整套皮肤。资料来源：

- [Tailwind Next.js Starter Blog](https://github.com/timlrx/tailwind-nextjs-starter-blog)：配置集中、内容优先、导航直接、主题和排版通过少量入口统一控制。
- [AstroPaper](https://github.com/satnaing/astro-paper)：标题层级克制、正文优先、响应式和键盘/辅助技术可用性是默认约束。
- [Next Shadcn Dashboard Starter](https://github.com/Kiranism/next-shadcn-dashboard-starter)：用成熟的 Button、Table、Command、Form、Drawer 等原语解决交互，不靠每个页面重新发明视觉语言。
- [Vercel Web Interface Guidelines](https://github.com/vercel-labs/web-interface-guidelines)：语义化控件、可见焦点、URL 反映状态、长文本可处理、避免 `transition: all` 等工程门槛。
- [Hallmark](https://github.com/Nutlope/hallmark)：先确定页面的宏结构、字体和色彩锚点，再审查是否出现模板化或“AI slop”；这里用于审查，不作为运行时依赖。

必须保留的差异：AgileCampus 是有任务状态、权限和 AI 交接的事务系统。博客模板的“文章列表”不能代替任务、验收和证据链，因此本计划只复用其内容层级和组件约束。

## 3. 固定的文案规则

### 3.1 词汇规则

使用“对象 + 状态 + 动作”的工程词汇：

| 场景 | 允许写法 | 禁止写法 |
| --- | --- | --- |
| 页面标题 | `项目资料`、`项目健康度`、`AI 成员` | `完整的项目不该只剩聊天记录`、`工作现场` |
| 任务状态 | `待处理`、`进行中`、`待验收`、`已完成`、`已阻塞` | `需要搭手`、`正在发光`、`眼下很稳` |
| AI 状态 | `AI 已生成草案`、`等待成员确认`、`已写入决策记录` | `像人一样工作`、`自己接活`、`会举手` |
| 风险 | `阻塞原因`、`影响范围`、`建议动作` | `卡住的活不会自己变好`、`不必先自己判断` |
| 空状态 | `暂无待验收任务` + `查看任务` | 一段项目宣言或安慰性说明 |
| 统计 | `待处理 3`、`进行中 2`、`待验收 1` | `3 项推进中 · 2 项需要关注` |

### 3.2 标点和排版规则

- 不把 `·`、`—`、`/` 当作字段分隔器。字段改成并列的 `MetaRow`、表格列或键值网格。
- `·` 仅允许用于真正的面包屑、日期范围、版本号、路径或外部 ID；不允许出现在页面标题、副标题、统计摘要和按钮文案中。
- 不使用全大写英文 eyebrow（如 `AI TEAMMATES`）做装饰。技术名词、状态名和按钮保持中文，必要的 API/ID 使用等宽字体。
- 不在每个标题下重复解释产品理念。辅助文字最多一行，且必须解释字段或下一步动作。
- 任何状态圆点必须同时有可读文本和可访问名称；圆点不能单独承担状态语义。
- 不使用“人性化、智能、轻量、无缝、完整、实时”等没有可验证含义的形容词，除非后面紧跟可验证的字段或指标。

### 3.3 AI 表述规则

AI 始终被描述为一个有输入、输出和权限边界的执行者：

- 输入：它读取了哪些项目资料、任务上下文或 GitHub 事件。
- 输出：它生成了任务草案、风险判断、决策比较、周报或代码变更建议中的哪一种。
- 状态：草案、等待确认、已确认、已拒绝、已写入。
- 责任：谁确认、谁验收、谁可以撤销。

示例：`AI 已根据 3 份资料生成任务拆解，等待项目负责人确认。`

禁止把 AI 写成“团队成员的替身”。`AI 成员`是产品实体名，不代表它拥有人的权限或自动改变任务状态。

## 4. 统一信息组件（先定结构，再改文案）

在业务页面批量替换前，先确认以下本地组件是否已存在；缺少时补到 `src/components/ui/`，沿用现有 tokens，不再引入新的主题系统。

### 4.1 `SectionHeader`

属性：`title`、可选 `count`、可选 `description`、可选 `action`。

- 只显示一个对象标题、一个数量和一个动作。
- `description` 限一行，描述字段含义，不描述产品愿景。
- 不支持 eyebrow、渐变标语或自动拼接的点号链。

### 4.2 `MetaRow`

属性：`label`、`value`、可选 `status`、可选 `action`。

- 用于负责人、状态、截止日、来源、更新时间、确认人。
- 桌面端使用两列或四列对齐；窄屏自动变成键值行。
- 值过长时换行或截断并保留完整 `title`，不得撑破布局。

### 4.3 `StatusBadge` 与 `ActorMark`

- `StatusBadge` 必须有文字：`进行中`、`待验收`、`已阻塞`等。
- `ActorMark` 明确显示 `成员` 或 `AI`，必要时显示具体名称；禁止仅显示“协作者”。
- 颜色只作为第二信号，不能只靠颜色区分状态。

### 4.4 `EmptyState`

属性：`title`、可选 `detail`、可选 `action`。

- 标题说清楚没有什么：`暂无待验收任务`、`暂无项目资料`。
- `detail` 只说明产生数据的条件或下一步，不写情绪化句子。
- 默认最多一个主动作；不堆叠“了解更多”“去看看”等弱动作。

## 5. 页面改造清单（按风险和访问频率执行）

### 阶段 A：更新产品语言基线

先更新 `docs/design/product-language.md`，加入本计划的词汇、标点、AI 责任边界和四字段原则。该文档是后续审查唯一基线，所有新文案先写入这里再进页面。

### 阶段 B：高频入口

#### B1. `src/app/(app)/today/page.tsx`

- 页面标题只保留 `今日`。
- 将“跨项目行动队列、按急迫度汇聚当下动作”等解释性句子改成明确筛选或数量，例如 `待处理任务`、`待验收任务`。
- 统计区拆为 `待处理`、`进行中`、`待验收` 三个键值单元，删除“1 项推进中 · 2 项需要关注”式摘要。
- 任务行必须出现：任务名称、项目、负责人、状态、截止时间、下一动作。
- 空状态直接写 `今天没有待处理任务`，动作写 `查看全部任务`。

#### B2. `src/app/(app)/projects/page.tsx`

- 项目卡片只保留项目名称、状态、负责人、更新时间和进入项目动作。

#### B3. `src/app/(app)/projects/[projectId]/workspace-view.tsx`

- “团队正在按计划推进，可以去任务流查看下一项交付”改为 `当前无阻塞`；若有阻塞，直接列出阻塞原因。
- `1 项推进中 · N 项需要关注` 改成对齐的统计单元。
- `查看 AI 工作现场` 统一为 `打开 AI 协作`，并保持现有深链接。

#### B4. `src/app/(app)/projects/[projectId]/_work/work-space.tsx`

- 任务卡默认展示状态、负责人、截止日、验收人和下一动作，不用装饰性标签堆叠。

### 阶段 C：项目四空间

#### C5. `src/app/(app)/projects/[projectId]/archive-section.tsx`

- 分支交接说明固定为：`从该消息继续`、`复制上下文`、`交给成员确认`。

## 6. 导航和交互不变，但信息入口要更短

- 保留现有两级侧边栏：一级导航展开二级导航；桌面可收起，窄屏为抽屉。
- 不新增第三层导航，不把页面标题、英文别名和功能入口重复放在项目卡片下方。
- 项目空间继续使用 `work`、`live`、`studio`、`record`，用户可见名称统一为 `工作`、`实时协作`、`AI 协作`、`记录`。
- 从 `/today` 到一个待处理任务最多两次点击；从任务抽屉到“请求协助/继续 AI 协作/提交验收”不超过一次额外点击。
- 所有筛选、展开、当前任务和会话分支继续反映到 URL，可复制、刷新和前进后退恢复。

## 7. 实施顺序与提交拆分

每个阶段单独提交，避免文案改动和业务逻辑混在一起：

1. `docs: define hard engineering copy rules`：更新产品语言基线，并加入本计划链接。
2. `refactor(ui): add structured information primitives`：补齐或统一 `SectionHeader`、`MetaRow`、`StatusBadge`、`ActorMark`、`EmptyState`。
3. `refactor(ui): rewrite today and project copy`：执行阶段 B，保持测试数据和动作不变。
4. `refactor(ui): rewrite project spaces and ai copy`：执行阶段 C，重点处理 Agent、上下文和决策记录。
5. `refactor(ui): rewrite library health and team copy`：执行阶段 D。
6. `test(ui): add copy and information hierarchy checks`：加入静态检查和关键路由回归。

任何阶段如果需要改 API、数据库、权限或任务状态机，必须另开计划，不得借文案重构顺手修改。

## 8. 自动检查和人工验收

### 8.1 静态检查

新增一个轻量脚本（建议 `scripts/check-ui-copy.mjs`），只扫描 `src/app/(app)` 和 `src/components` 的可见 JSX/TSX 文本：

- 报告禁用短语：`不该只剩`、`眼下都还稳`、`有人在等搭手`、`像人一样`、`自己接活`、`会举手`、`AI TEAMMATES`、`就地搭手`。
- 报告标题/副标题中的 `·`、`—`、`/` 链式分隔；允许列表写入明确白名单（面包屑、日期、路径、外部 ID）。
- 报告以大写英文作为装饰 eyebrow 的新增文本。
- 不扫描 API、测试 fixture、注释和许可证文本，避免误报。

命令加入 `package.json`：`npm run check:ui-copy`。CI 顺序为 `npm run check:ui-copy && npm run lint && npx tsc --noEmit && npm run build`。

### 8.2 路由回归

在桌面和窄屏各走一遍以下路径：

1. `/today`：打开一项任务，确认负责人、状态、截止日、下一动作可读。
2. `/projects`：进入项目，确认两级侧边栏展开，项目卡无重复入口。
3. `?space=work`：拖拽只改变分组，不改变任务状态；任务抽屉可提交待验收。
4. `?space=live`：查看 AI 执行记录、输入来源、输出和阻塞动作。
5. `?space=studio`：从现有会话继续，不丢失分支和上下文来源。
6. `?space=record`：查看决策、证据、反馈、文档和成果；可导出项目档案。
7. `/library`、`/health`、`/collaboration`、团队 AI 成员页面：确认空状态、统计和操作均为直白工程词汇。

### 8.3 视觉和可用性验收

- 首屏不出现宣传性大段文字；页面标题、对象和主动作在视觉上最突出。
- 不出现独立装饰圆点、虚线框或只为“有设计感”而存在的分隔符。
- 状态颜色有文本伴随；键盘可见焦点保留；按钮使用语义化 `<button>` 或 `<a>`。
- 长任务名、文件名、Agent 名称和项目名不会撑破卡片或表格。
- `prefers-reduced-motion` 下不影响完成任务；不使用 `transition: all`。
- 颜色、字体、间距和圆角只来自现有 tokens；不引入博客模板的默认主题色。

## 9. 完成判定

当且仅当以下条件全部满足，计划可标记完成：

- 高频页面已完成阶段 B，四空间和协同/资料/健康度页面已完成阶段 C、D。
- 禁用短语和未授权分隔符检查通过；新增文案先进入产品语言基线。
- 核心路径的业务动作、权限和 URL 状态与改造前一致。
- 桌面和 615px 左右窄屏验收通过，侧边栏、抽屉、任务详情和 AI 分支可用。
- `npm run check:ui-copy`、`npm run lint`、`npx tsc --noEmit`、`npm run build` 和现有测试全部通过。
- 变更说明中列出：删掉了哪些宣传性文案、替换成了哪些字段、哪些点号链改成了哪些结构化行，以及 AI 输出的确认边界是否仍清晰。
